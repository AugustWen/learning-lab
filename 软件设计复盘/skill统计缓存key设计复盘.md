# 一、业务建模原则

## 1. 先建模业务事实，再选择存储结构

### 原则

不要从 Redis、MySQL、Kafka 等具体组件提供的数据结构出发设计业务模型。

应先描述业务中实际存在的实体、维度、关系和生命周期，再把业务模型映射到具体存储结构。

### 常见错误

一开始就思考：

* Redis key 应该如何拼接？
* 数据应该放在 hash field 还是 value？
* 是否可以通过一个大 hash 保存所有内容？

却没有先回答：

* 一条统计记录代表什么？
* 哪些字段属于统计维度？
* 哪些字段属于指标？
* 哪些数据需要一起读取、删除和过期？

### 检查问题

在设计存储结构前，先尝试写出逻辑模型：

```text
StatisticRecord {
    timeBucket
    skillName
    functionName
    expId
    metrics
}
```

如果逻辑模型本身还不清晰，不应急于确定 Redis key。

---

## 2. 配置描述预期，事件描述事实

### 原则

配置数据通常表示系统希望存在哪些内容；实时请求或业务事件表示实际上发生了什么。

统计、审计和监控系统应优先记录实际发生的事实，不能把配置集合直接当成事实全集。

### 示例

```text
配置中声明的 function 集合
≠
运行期间实际被调用的 function 集合
```

配置可能：

* 存在漏项；
* 尚未及时刷新；
* 与灰度版本不一致；
* 无法覆盖动态路由；
* 无法覆盖历史或异常请求；
* 只描述部分来源。

### 推荐关系

```text
事件决定记录什么
配置帮助解释、校验和展示事件
```

而不是：

```text
配置中存在，事件才允许被记录
```

---

## 3. 不要把当前可枚举的集合视为永久全集

### 原则

当前能够从配置、枚举或代码中拿到完整集合，不代表这个集合未来仍然完整。

设计时要区分：

* 业务上封闭的集合；
* 当前实现中暂时可枚举的集合；
* 运行时不断出现的开放集合。

### 典型开放集合

* 请求中实际出现的 function；
* 用户 ID；
* 实验 ID；
* 错误码；
* 调用方；
* 模型版本；
* 插件或工具名称。

### 检查问题

当自己准备依赖某个“全集”时，应询问：

> 这个集合是由业务规则保证封闭，还是因为当前只有一个数据来源，所以看起来完整？

---

# 二、数据结构设计原则

## 4. 一个存储单元应代表清晰的聚合对象

### 原则

一个 Redis key、数据库行或文档，应尽量代表一个语义明确的业务对象或聚合单元。

同一个存储单元中的数据最好具有相似的：

* 更新方式；
* 读取方式；
* 删除方式；
* 生命周期；
* 过期时间；
* 权限边界。

### 示例

```text
stat:{timeBucket}:{skillName}:{functionName}:{expId}
```

该 key 表示：

> 某个时间窗口内，某个 Skill 的某个 Function 在某个实验下的统计对象。

hash 中保存：

```text
request_count
success_count
failure_count
latency_sum
```

这些指标通常会被一起更新、读取和过期，因此可以组成一个合理的聚合单元。

---

## 5. 维度和指标应尽量分离

### 原则

统计模型通常可以拆分为：

```text
统计对象 = 维度组合
统计结果 = 指标集合
```

例如：

```text
维度：
- timeBucket
- skillName
- functionName
- expId

指标：
- requestCount
- successCount
- failureCount
- latencySum
```

### 风险信号

当 hash field 逐渐变成：

```text
expId::functionName::region::modelVersion::metricName
```

说明 field 已经承担了一套自定义编码协议。

这种结构通常会造成：

* 语义不清晰；
* 解析逻辑分散；
* 删除部分数据困难；
* 无法独立设置生命周期；
* 新增维度时持续修改拼接规则；
* 查询代码越来越依赖字符串处理。

---

## 6. 数据结构要同时考虑读取和写入

### 原则

不能只因为写入简单就确定数据结构。

设计前需要列出主要查询模式，例如：

1. 查询某个 Skill、Function、实验的所有指标；
2. 查询某个 Skill 下实际出现过哪些 Function；
3. 查询某个实验下有哪些 Function；
4. 找出配置外但实际发生调用的 Function；
5. 删除某个时间窗口的数据；
6. 聚合小时和天级别统计；
7. 为数据设置过期时间。

然后判断主数据结构能否支持这些访问模式。

### 提醒

Redis 不是关系数据库。为了支持枚举或反向查询，维护额外的 Set、Sorted Set 或其他索引并不天然是坏设计。

判断标准不是“有没有额外数据结构”，而是：

> 这个额外结构是在补偿错误模型，还是在为明确的查询模式建立索引？

---

## 7. 索引应服务于真实查询，而不是无限预建

### 原则

主数据结构负责保存事实，辅助结构负责支持必要的访问路径。

例如：

```text
主数据：
stat:data:{bucket}:{skill}:{function}:{expId}

实际出现的 Function 索引：
stat:functions:{bucket}:{skill}

实际出现的实验索引：
stat:experiments:{bucket}:{skill}:{function}
```

Set 的存在可以是合理的二级索引。

但不应该为每一种未来可能出现的组合提前创建索引，因为这会产生：

* 写放大；
* 存储放大；
* 数据一致性维护成本；
* 无效索引；
* 更复杂的过期和清理逻辑。

---

## 8. 生命周期不同的数据不要轻易放进同一个大 Key

### 原则

Redis 的过期通常作用于整个 key，而不是单个 hash field。

如果一个大 hash 中的数据具有不同的：

* 时间窗口；
* 实验生命周期；
* 删除条件；
* 数据保留期限；

把它们放入同一个 key 会导致清理和过期困难。

### 风险

使用：

```text
key = stat:{skillName}
field = expId::functionName::metric
```

虽然看起来集中，但可能出现：

* 单 key 过大；
* 单点热 key；
* 所有写入集中；
* 局部删除需要扫描；
* 不能独立过期；
* 新维度继续扩大 field 数量。

---

# 三、变化与扩展原则

## 9. 设计扩展点，不等于预测所有需求

### 原则

良好的设计不是提前预测所有未来字段和需求，而是：

* 显式表达已经确定的核心概念；
* 降低新增相邻维度时的修改范围；
* 避免把当前偶然条件写入核心模型；
* 保留清晰的重构边界。

### 错误极端

因为害怕未来变化，设计出完全动态的结构：

```text
dim1::dim2::dim3::dim4::metric
```

或者试图一次性实现通用统计平台。

这往往会牺牲：

* 类型约束；
* 可读性；
* 可观测性；
* 查询效率；
* 维护成本。

### 推荐思路

对于已经明确的核心维度，应显式建模。

对于未来可能出现但尚不明确的维度，不必立即泛化，而要确保以后增加时不会破坏全部结构。

---

## 10. 识别并记录设计中的隐含假设

### 原则

很多设计问题不是代码错误，而是隐含假设失效。

设计评审时应主动写出假设，例如：

```text
假设一：Function 全部来自 SkillConfig。
假设二：统计指标集合由当前服务完整控制。
假设三：实验 ID 不参与统计维度。
假设四：所有统计数据具有相同生命周期。
```

然后逐一判断：

* 这个假设由谁保证？
* 是业务规则还是当前实现？
* 失效后影响范围多大？
* 是否需要通过代码校验？
* 是否需要通过监控发现？

能够显式说出假设，比试图凭经验预测所有需求更可靠。

---

## 11. 暴露稳定的业务语义，而不只是自己掌握的数据

### 原则

“尽可能暴露自己掌握的东西”并不是完整原则。

更准确的表达是：

> 对外提供稳定、明确、具有唯一语义的业务能力，避免暴露容易变化的内部实现细节。

一个字段是否由自己掌握，并不能单独决定它是否应该成为接口或模型的一部分。

判断时要考虑：

* 它是不是必要的业务事实？
* 它的语义是否稳定？
* 它是否有唯一可信来源？
* 调用方是否必须依赖它？
* 变化时兼容成本如何？
* 它是领域概念，还是当前实现细节？

### 示例

`functionName` 即使不完全由统计服务掌握，仍然是不可绕过的业务事实。

而“Function 来自 SkillConfig 的第几个数组元素”即使当前服务能够获取，也属于不稳定的实现细节，不适合暴露。

# 四、案例：Skill 调用统计的 Redis 结构演进

## 1. 背景

系统需要统计 Skill 下不同 Function 的调用情况。

统计指标包括：

* 调用次数；
* 成功次数；
* 失败次数；
* 延迟等。

最初认为所有 Function 都可以从 Skill 配置中获取，因此统计时可以依赖配置拿到 Function 全集。

---

## 2. 初始设计

第一种思路：

```text
key = XXXX:SKILLNAME:统计指标
```

由于统计指标由当前服务定义，可以通过配置或代码获得指标全集。

后续调整为：

```text
key = XXXX:SKILLNAME:FUNCTIONNAME
hash field = 指标
```

这个结构在只有 Skill、Function 和指标时可以工作。

---

## 3. 第一次扩展：增加 AB 实验维度

后续需求要求按照 `expId` 区分统计数据。

为了兼容现有结构，将 hash field 修改为：

```text
expId::指标
```

最终结构近似：

```text
key = XXXX:SKILLNAME:FUNCTIONNAME
hash field = expId::metric
```

### 暴露的问题

`functionName` 位于 Redis key，`expId` 和指标位于 hash field。

不同统计维度分布在不同层级，数据结构缺少一致的领域含义。

如果继续增加地区、版本或调用方等维度，field 可能继续演变为：

```text
expId::region::version::metric
```

---

## 4. 第二次扩展：统计配置之外的 Function

后续发现 Function 不完全来自 SkillConfig，还可能来自：

* reference；
* 其他 Skill 数据结构；
* 实时请求；
* 动态来源。

为了统计这些 Function，新增一个 Set，记录实时请求中出现过的 Function，在统计阶段查询该 Set。

### 表面现象

方案通过增加 Set 完成了需求，但感觉像在原有模型上不断打补丁。

### 根本原因

原模型存在一个没有显式写出的假设：

```text
实际发生调用的 Function 集合
=
SkillConfig 中配置的 Function 集合
```

这个假设不成立。

SkillConfig 只能代表部分预期配置，不能代表实际流量事实的全集。

---

## 5. 对案例的原则分析

### 问题一：从配置推导事实

统计系统应该记录请求中实际出现的 Function，而不是只统计配置中预先存在的 Function。

配置可以用来：

* 展示预期 Function；
* 对未调用的 Function 补零；
* 校验未知 Function；
* 标记异常调用；
* 丰富名称和元数据。

但配置不应决定一条真实调用是否被统计。

对应原则：

* 配置描述预期，事件描述事实；
* 不要把当前可枚举集合视为永久全集。

### 问题二：Redis 结构先于业务模型

早期设计主要考虑指标放在哪里、key 如何拼接，却没有先完整表达：

```text
一条统计记录由哪些维度唯一确定？
```

更清晰的逻辑模型是：

```text
StatisticRecord {
    timeBucket
    skillName
    functionName
    expId
    metrics
}
```

对应原则：

* 先建模业务事实，再选择存储结构；
* 维度和指标应尽量分离。

### 问题三：Set 是否属于补丁

Set 本身不一定是补丁。

如果 Set 用于记录实际出现过的 Function，并支持以下查询：

```text
某个 Skill 在一个时间窗口内出现过哪些 Function？
```

那么它可以被定义为主统计数据的二级索引。

真正需要修正的是：

* 主数据是否直接记录实际事件；
* Set 的用途是否明确；
* Set 与主数据是否具有一致的时间窗口和过期策略；
* 写入失败时是否允许索引与主数据暂时不一致。

对应原则：

* 索引服务于真实查询；
* 判断额外结构是在修补模型，还是建立访问路径。

---

## 6. 候选改进方案

按时间窗口统计时，可以采用：

```text
key = stat:{timeBucket}:{skillName}:{functionName}:{expId}
hash field = metricName
```

例如：

```text
stat:2026073110:skillA:functionA:exp123
```

hash 内容：

```text
request_count = 100
success_count = 95
failure_count = 5
latency_sum = 23000
```

无实验时使用明确的占位值：

```text
noexp
```

为了列举实际出现过的 Function，可以维护：

```text
stat:functions:{timeBucket}:{skillName}
```

Set 内容：

```text
functionA
functionB
functionUnknown
```

这个方案表达的含义是：

* 主 key 表示一个明确的统计对象；
* hash field 表示该统计对象的各项指标；
* Set 表示某个查询维度下实际出现过的对象索引。

---

## 7. 仍需结合实际场景确认的问题

不能仅凭抽象原则确定最终 Redis 结构，还要验证：

1. 统计数据按分钟、小时还是天过期？
2. 单个 Skill 的 Function 和实验数量上限是多少？
3. 最常见的读取方式是什么？
4. 是否需要一次查询整个 Skill 的全部统计数据？
5. Redis 是否使用 Cluster？
6. 是否要求相关 key 落在同一个 slot？
7. 写入吞吐量和热点分布如何？
8. Set 索引与主统计数据是否必须强一致？
9. 最终统计是否会落库或进入离线分析系统？
10. Redis 承担实时聚合，还是作为最终统计存储？

只有结合数据规模、查询模式和生命周期，才能在小 key、大 hash、索引数量和集群分布之间做最终取舍。

---

## 8. 本案例形成的核心结论

### 结论一

不要围绕当前配置设计统计模型，应围绕实际发生的业务事件设计。

### 结论二

配置用于描述、解释和校验事实，不应被默认当成事实全集。

### 结论三

先明确统计维度和指标，再把它们映射为 Redis key、hash 和索引。

### 结论四

新增 Set 不一定是坏补丁。为真实查询建立二级索引是 Redis 中常见且合理的设计方式。

### 结论五

好的扩展性不是预测所有需求，而是避免核心模型依赖容易失效的偶然假设。

### 结论六

对外暴露的应是稳定、明确的业务语义，而不只是当前服务自己能够掌握的数据。
