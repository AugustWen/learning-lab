## 案例：周期同步任务中的调度漂移与分布式批次去重

### 1. 背景

系统需要将 Redis 中的统计数据周期性同步到 Data 服务。

最初 Redis 保存全天全量统计数据，但为了提高容灾能力，避免 Redis 异常时丢失全天数据，后来改为增量模式：

- 业务请求持续通过 `HINCRBY` 写入增量数据。
- 每 10 分钟执行一次同步任务。
- 同步时通过 Lua 脚本原子执行 `HGETALL + DEL`，取走当前增量。
- 同步成功后无需处理。
- 同步失败后，通过 `HINCRBY` 将本批次增量重新回写，与同步期间新产生的数据自然合并。
- 不要求当前批次立即重试，只要不跨天，下一周期即可补偿同步。

系统部署多个节点，每个节点都会运行定时任务，通过 Redis 分布式锁保证只有一个节点执行同步。

---

### 2. 初始设计

调度逻辑：

```text
首次计算到下一个整点/10分钟对齐点的等待时间
        ↓
等待
        ↓
执行 doSync()
        ↓
创建 time.Ticker(10min)
        ↓
每 10 分钟再次执行
```

分布式协调：

```text
SET lock NX EX ...
        ↓
执行同步
        ↓
DEL lock
```

初看设计合理：

- Scheduler 控制周期执行。
- Redis Lock 控制多节点互斥。
- Lua 保证 Redis 增量读取原子性。
- HINCRBY 保证失败回写不会覆盖新数据。

但线上发现两个节点的同步完成时间非常接近，例如：

```text
02:20:07 node A completed
02:20:14 node B completed
```

并怀疑存在部分统计数据遗漏。

---

## 3. 问题一：周期任务发生时间漂移

问题代码的本质是：

```text
执行 doSync()
        ↓
任务执行完成
        ↓
才创建 ticker
```

假设目标周期为 10 分钟：

```text
02:20:00 doSync 开始
02:20:07 doSync 完成
02:20:07 创建 ticker
```

那么下一次执行时间变成：

```text
02:30:07
```

而不是：

```text
02:30:00
```

因此实际语义不是：

> 每 10 分钟的 wall-clock 对齐点执行。

而是：

> 从上一次任务执行完成时间开始，再等待 10 分钟。

任务耗时因此被带入下一轮调度基准，形成漂移。

### 修正

对于需要按真实时间对齐的周期任务，不应该依赖一次创建后的固定 Ticker。

应在每一轮重新计算：

```text
当前时间
    ↓
下一个 10 分钟对齐点
    ↓
等待对应 duration
    ↓
执行
    ↓
重新计算
```

例如：

```text
02:20:00 开始
02:20:07 完成

重新计算：
next = 02:30:00

等待 9m53s
```

这样任务耗时不会影响下一次逻辑执行时间。

### 经验

需要区分两类定时任务：

**固定间隔任务**

```text
上一次执行后过 10 分钟再执行
```

适合 `Ticker`。

**Wall-clock 对齐任务**

```text
每小时整点
每 10 分钟整点
每天 00:00
```

应该每轮重新计算目标时间。

---

## 4. 问题二：分布式锁解决了错误的问题

最初使用普通 Redis 分布式锁：

```text
SET lock NX
执行
DEL lock
```

它保证的是：

> 某个时刻最多一个节点正在执行。

但业务真正需要的是：

> 某一个逻辑时间批次，全局最多执行一次。

这是两种完全不同的语义。

例如：

```text
02:20:00
Node A 获取锁

02:20:07
Node A 执行完成
Node A DEL lock

02:20:08
Node B 获取锁
Node B 再次执行
```

整个过程中并不存在并发执行，因此普通 mutex 完全没有失效。

但 `02:20` 这个逻辑批次却执行了两次。

### 核心认知

问题不在于：

```text
锁不够强
```

而在于：

```text
锁的抽象层次与业务约束不一致
```

业务约束是“批次唯一性”，却使用了“瞬时互斥”模型。

---

## 5. 改进：从 Mutex 改为 Batch Slot Claim

将每个 10 分钟周期定义为一个逻辑 slot：

```text
02:00
02:10
02:20
02:30
...
```

例如：

```text
slotID = 202609290220
```

Redis Key：

```text
statistics:sync:slot:202609290220
```

所有节点针对同一个时间批次执行：

```text
SET slotKey nodeID NX EX 86400
```

成功：

```text
当前节点取得该批次执行权
```

失败：

```text
该批次已经被其他节点认领
当前节点直接跳过
```

最重要的一点：

```text
执行结束后不 DEL slot key
```

Slot Key 依靠长 TTL 自动清理。

因此：

```text
Node A claim 02:20 成功
Node A 执行完成

Node B 即使 10 秒后才触发
仍然无法再次 claim 02:20
```

这才真正满足：

> 一个逻辑批次最多执行一次。

---

## 6. 为什么不采用“延迟释放锁”

一种直觉方案是：

```text
所有节点尽量整 0 秒启动
+
任务结束后延迟几秒释放锁
```

这种方式只能缩小问题发生概率。

因为它仍然基于：

```text
现在有没有人在执行
```

而不是：

```text
这个批次有没有执行过
```

只要出现：

- 调度延迟
- GC pause
- 进程启动时间差异
- 网络抖动
- 节点重启
- 某节点晚几十秒触发

仍然可能在锁释放后重复执行当前批次。

因此：

> 延迟释放属于时间窗口补丁，Slot Claim 属于语义层修复。

---

## 7. 增量数据设计为什么能够自然支持失败补偿

Redis 统计数据采用：

```text
业务持续 HINCRBY
```

同步时：

```text
Lua:
HGETALL
DEL
```

保证“读取当前增量”和“清空当前增量”原子完成。

例如同步任务取走：

```text
100
```

任务执行期间新请求又写入：

```text
20
```

此时 Redis 中是：

```text
20
```

如果同步失败，则：

```text
HINCRBY +100
```

最终 Redis：

```text
120
```

因此：

- 不覆盖新数据。
- 不要求当前批次立即 retry。
- 下一轮能够自然补偿。

这是一个典型的：

> 原子交换 + 增量回写

模式。

相比全天全量 Redis 数据，它将故障损失范围由：

```text
最多一天
```

降低到：

```text
最多一个同步周期
```

## 8. Data 服务暴露出的另一层风险：Read-After-Write 假设

同步过程本质是：

```text
GET Data 历史累计值
        ↓
历史值 + Redis 本批次增量
        ↓
PUT Data 新累计值
```

属于典型 Read-Modify-Write。

如果短时间内连续执行两个批次：

```text
A PUT 1100
        ↓
B GET
```

代码实际上隐含了一个假设：

> Data 服务 PUT 成功返回后，下一次 GET 必须能够读到最新值。

但 Data 服务即使没有缓存，也可能存在：

- 异步写入
- 内部聚合
- 多副本同步
- 读写节点差异
- 持久化延迟

因此“接口返回成功”和“后续读取立即可见”并不是天然等价的。

如果：

```text
Data 初始 = 1000

A:
delta = 100
PUT 1100
return success

B:
马上 GET
却仍读到 1000

delta = 10
PUT 1010
```

就可能产生覆盖式丢数据。

Slot Claim 的另一个价值在于：

```text
正常情况下，相邻两次 Read-Modify-Write 间隔约 10 分钟
```

大幅降低 Data 服务短暂可见性延迟带来的风险。

但更根本的工程原则仍是：

> 对外部服务的一致性保证必须显式确认，而不能依赖实现猜测。

## 9. 最终设计职责划分

整个同步系统可以拆成四层：

### Scheduler

负责：

```text
什么时候应该尝试执行
```

采用 wall-clock 对齐。

---

### Batch Slot Claim

负责：

```text
这个逻辑批次是否已经被其他节点执行
```

保证批次去重。

---

### Redis Increment Snapshot

负责：

```text
安全取走当前统计增量
```

通过：

```text
HGETALL + DEL Lua
```

完成原子交换。

失败时：

```text
HINCRBY
```

完成增量补偿。

---

### Data Service

负责：

```text
累计统计结果持久化
```

需要明确其：

```text
write success
read-after-write consistency
```

等接口语义。

---

## 10. 最终架构

```text
       Wall Clock
           ↓
  02:20 / 02:30 / 02:40
           ↓
       Scheduler
           ↓
    Calculate Slot ID
           ↓
202609290220
           ↓
 Redis SET NX Slot Claim
           ↓
       claim success
           ↓
 Lua HGETALL + DEL
           ↓
   Redis Delta Snapshot
           ↓
      Data GET
           ↓
     old + delta
           ↓
      Data PUT
           ↓
        success
```

失败：

```text
Data PUT failed
      ↓
HINCRBY delta back
      ↓
下一周期继续处理
```

## 11. 这次设计问题的核心经验

### 经验一：先定义业务语义，再选择并发原语

不要看到“多节点只能一个执行”就直接想到分布式锁。

先问：

```text
我要保护的是临界区？
还是我要保证一个业务事件只处理一次？
```

前者是 Mutex。

后者更接近：

```text
Idempotency Key
Event ID
Batch ID
Slot Claim
```

---

### 经验二：时间也是系统状态的一部分

“每 10 分钟执行”至少有两种不同含义：

```text
每隔 10 分钟
```

和：

```text
每个 10 分钟时间边界
```

设计调度系统时必须明确到底是哪一种。

---

### 经验三：不要用时间窗口补丁代替业务唯一标识

例如：

```text
延迟释放锁
sleep 5 秒
所有节点整 0 秒启动
```

这些都只能降低概率。

如果业务本身存在：

```text
batchID
requestID
eventID
```

就应该直接利用业务 ID 建模。

---

### 经验四：Read-Modify-Write 必须明确一致性前提

任何：

```text
read
modify
write
```

都应该问：

```text
是否存在多个 writer？
写成功后什么时候可读？
是否可能 stale read？
是否有原子更新接口？
是否能设计成幂等增量接口？
```

不能因为“没有缓存”就默认强一致。

---

### 经验五：失败恢复模型要与数据结构共同设计

这次 Redis 增量模式的优势在于：

```text
原子取走
+
失败增量回写
+
下一批次自然补偿
```

因此不需要额外构建复杂的任务 retry / lease takeover。

恢复机制不是 Scheduler 独立决定的，而应该结合：

```text
数据模型
幂等能力
业务容忍度
补偿方式
```

一起设计。

---

## 12. 一句话总结

这次问题表面是：

> 多节点 10 分钟定时任务执行时间异常。

真正的问题是：

> **用“瞬时互斥锁”解决了“批次唯一性”问题，同时混淆了固定间隔时间与 wall-clock 时间语义。**

最终设计通过：

```text
Wall-clock Scheduler
+
Batch Slot Claim
+
Redis Atomic Increment Snapshot
+
Failure Compensation
```

把调度、去重、数据一致性和失败恢复四个问题拆开，各自使用与业务语义匹配的机制。
